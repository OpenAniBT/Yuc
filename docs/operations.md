# 维护说明

## 本地同步

在仓库根目录、已安装 `requirements.txt` 依赖的 Python 3.13 环境中运行：

```bash
python -m unittest discover -s tests -v
python -m yuc sync
python -m yuc validate
python -m yuc health
git diff --stat -- data/
```

默认同步遍历全部归档分页，并沿首页文章链接、文章正文和相邻文章链接发现页面。已有文章优先使用 ETag，缺少 ETag 时使用 Last-Modified 发起条件请求；服务端返回 `304` 时读取已保存的 HTML。`python -m yuc sync --full` 不发送这些条件请求头，强制获取页面内容。

两种模式都会用当前解析器处理全部文章。因此解析器更新后，普通同步也能重新生成 JSON。HTML 字节未变化时保留先前的来源信息和 `retrievedAt`；发现证据也按内容散列保留来源记录。`status.json` 单独记录本次检查时间，正常的无内容变化同步也会提交状态更新。

同步会遵守 `robots.txt`，核对归档分页声明的文章总数，不会自动删除从发现清单中消失的旧文章。这些文章保留在归档中，并记入 `retainedUrls`。单页抓取、解析或校验失败时，保留该页上次有效快照，继续检查其他页面；尚无快照的新页面记入 `pendingUrls`。候选归档通过离线校验后，再逐文件替换发生变化的内容。不要同时启动多个本地同步进程。

发现阶段失败时，程序沿用已验证的发现证据，并在本次 `robots.txt` 策略允许的情况下继续检查已知页面。无法取得或确认本次抓取策略时，不再抓取页面，只对已有归档发布降级状态。首次归档没有可安全沿用的发现证据时，失败属于致命错误。

`/new/` 是滚动更新的预告页，换季时可能一次移除大量旧预告。同步会检查文章尾部是否存在，并核对原始 HTML 中的卡片、表格、标题与 JSON 条目是否完整对应；通过后接受来源中的数量变化。减少的数量写入运行输出和 `reports/sync.json` 的 `sourceChanges`，旧内容仍保存在 Git 历史中。其他集合保留原有的数量异常下降检查。

每次同步输出本次完成时间、变更文件、条目汇总及失败详情，并写入 `reports/sync.json` 和 `reports/summary.md`。致命错误也会替换上次报告，避免误读旧的成功结果。报告目录无法写入时，命令返回 `1` 并在日志中说明；此时不能保证文件报告可用。运行报告不纳入 Git，`--report-dir` 可指定其他目录。

| `sync` 退出码 | 含义 | 后续操作 |
| --- | --- | --- |
| `0` | 已发布健康归档 | 离线校验后可提交 |
| `2` | 已发布可验证的降级归档 | 离线校验后可提交有效更新和失败状态，再排查失败页面 |
| `1` | 致命错误，未完成安全发布 | 检查日志，不提交本次工作目录中的归档变更 |

单页失败第一次产生 Actions warning，连续降级达到 3 次后产生 error annotation。无论是否达到 3 次，降级状态都会使健康检查失败。恢复成功后，相应失败计数归零并清除错误。`reports/rejected/` 在可取得响应时保存受大小限制的公开 HTML 和错误元数据；它是诊断证据，不是已接受的归档快照。

原始 HTML 用于核对结构化字段。遇到页面布局变化，先对照 `data/raw/` 中对应页面，再修改解析器；不要直接改写归档结果掩盖解析差异。

## HTTPS 连接

抓取器首先按 DNS 解析结果连接 `https://yuc.wiki/`。这条路径失败时，尝试直接连接 GitHub Pages 地址 `185.199.108.153`，同时保持 HTTP Host 和 TLS SNI 为 `yuc.wiki`，使用系统信任库完整验证证书。成功路径成为本次运行的首选；后续请求失败时仍会尝试另一条路径。

单个请求的跳转、重试和读取共用 50 秒预算；socket 超时最多 10 秒。网络临时错误、HTTP 429 和 5xx 才会重试，`Retry-After` 最多等待 5 秒。整个抓取阶段达到 10 分钟预算后，不再开始新请求，剩余页面保留旧快照并标记失败。当前 Actions 和 POSIX 主线程 CLI 使用进程定时器覆盖 DNS 阻塞等情况；非 POSIX、非主线程或已有进程定时器时，无法保证这些特殊阻塞在 50 秒内被中断。

两条路径都不允许跳过 TLS 校验。连接方式写入 `source.transport`；备用地址不是另一内容来源。若两条路径均失败，修复网络、源站证书或核实 Pages 地址后重试。

## 离线校验

`python -m yuc validate` 不访问网络。它检查每页 JSON Schema、原始 HTML 散列、来源和 manifest 一致性、条目与页面计数、发现证据散列，并从原始 HTML 重新解析以验证 JSON 可复现。显式记录的 `pendingUrls`、历史保留页面及降级状态可通过一致性校验；校验成功不表示本次抓取全部成功。原始文件损坏、索引遗漏或 JSON 与 HTML 不一致须修复后再提交。

`python -m yuc health` 同样不访问网络。它读取 `data/status.json`，并要求状态为 `healthy`、检查时间距当前 UTC 不超过 24 小时。降级、过期、缺失或无效状态返回 `1`，健康且及时的状态返回 `0`。旧归档缺少状态文件时，先执行一次同步。检查时间为将来且超过允许的时钟偏差时，也不能判为及时。`health` 不会发起抓取或更新状态。

## GitHub Actions

| 工作流 | 触发方式 | 行为 |
| --- | --- | --- |
| Validate archive | Push、Pull Request | 安装依赖，运行测试和已提交归档校验 |
| Sync Yuc archive | 每 6 小时、每周日完整抓取、手动运行 | 测试、同步、校验、提交 `data/`，最后检查健康状态 |

定时计划为 UTC：增量同步在每天 `00:17`、`06:17`、`12:17`、`18:17`；完整抓取在每周日 `02:43`。GitHub 的定时任务可能延迟，不构成实时更新承诺。

手动运行时，进入仓库 **Actions → Sync Yuc archive → Run workflow**，选择默认分支。通常保持 `full` 关闭；需要绕过条件请求时开启。写入工作仅在默认分支运行，使用统一 concurrency group 排队，防止多个同步任务同时写入。

工作流使用 GitHub 官方 `actions/checkout`、`actions/setup-python` 和 `actions/upload-artifact`，均固定到完整提交 SHA。升级时核对官方仓库标签对应的提交，同时更新版本注释。Python 依赖版本由 `requirements.txt` 固定。

同步返回 `0` 或 `2` 时，工作流校验归档并提交有效变更，随后运行健康检查。返回 `1`、测试失败或离线校验失败时，不执行提交步骤。摘要和报告上传步骤使用 `always()`，在运行失败后仍尝试执行；安装依赖或测试阶段失败、尚未生成同步报告时，摘要提示查看对应步骤日志。报告 artifact 保留 14 天。

通知使用 GitHub Actions 的运行结果、annotation 和 job summary；需要邮件通知时，在 GitHub 账户通知设置中配置 Actions 通知。仓库不创建外部通知服务、Slack 消息或故障 issue。定时任务若完全未启动，本工作流无法自行产生新的失败通知；应结合最新 Actions 运行记录及 `health` 检查判断是否漏跑。

## 身份与权限

维护者从本机克隆和推送时使用 SSH：

```bash
git remote get-url origin
# git@github.com:AniBT-Net/Yuc.git
git push origin main
```

托管 Actions 使用当前运行的临时 `GITHUB_TOKEN`。只有同步工作具有 `contents: write` 权限；校验工作只有读取权限。无需创建 SSH secret，也不需要长期有效的个人访问令牌。

仓库或组织策略必须允许同步工作取得内容写入权限，默认分支规则也必须允许该身份提交归档更新。如果推送被策略拒绝，应检查工作流日志与仓库策略，不要关闭校验或使用强制推送。

由 `GITHUB_TOKEN` 创建的推送通常不会再次触发 Push 工作流，因此同步工作在提交前自行执行全部测试和 `python -m yuc validate`。

## 失败处理

- 源站不可达、TLS 校验失败或抓取报错：查看同步步骤日志和连接路径。普通 HTTPS 与 GitHub Pages 备用路径均须通过证书验证；修复源站或网络问题后重试。
- 发现数量减少或条目数量异常下降：对照 `data/raw/discovery/`、`reports/rejected/` 与相关文章 HTML，确认源站变化及解析器行为后修复；旧文章不会自动删除。预告页正常换季减少可通过来源覆盖检查；`upcoming source coverage mismatch` 表示卡片、表格、标题与解析结果不对应，`incomplete upcoming article` 表示文章尾部结构缺失，均应检查原始页面后修复。
- 测试或归档校验失败：工作流不会执行提交步骤。对照原始 HTML 和解析结果修复后重跑。
- 推送被拒绝：检查令牌权限、默认分支保护和是否有同期人工推送。工作流不执行强制推送；从最新默认分支重新运行即可。
- 定时运行未出现：检查 Actions 是否启用、工作流是否已在默认分支，以及 GitHub 是否暂停了长期无活动仓库的定时任务。

因健康检查失败的降级运行，可能已经提交了其他页面的有效更新和本次失败状态。致命错误或校验失败的运行不会提交数据；推送失败时，本地提交也不代表远程已更新。判断结果时，结合提交与推送步骤、`data/status.json` 和报告，不要只看工作流的最终颜色或页面 `retrievedAt`。
